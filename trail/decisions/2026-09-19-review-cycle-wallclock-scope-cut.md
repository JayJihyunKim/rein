# 리뷰 대기 시간 단축 — 14개 태스크 계획 중단, 판정 시간 로그만 남기고 범위 축소

- 날짜: 2026-09-19
- 결정자: 사용자 (독립 검토 의견을 받은 뒤 승인)
- 대상: `docs/specs/2026-09-11-review-cycle-wallclock.md`, `docs/plans/2026-09-14-review-cycle-wallclock.md`, `trail/dod/dod-2026-09-15-review-cycle-wallclock.md`

## 결정

1. 계획의 첫 태스크(판정으로 끝난 리뷰 호출의 시간 로그)만 좁은 범위로 닫는다. 나머지 13개 태스크와 보류돼 있던 2축(관찰 체크포인트·델타 리뷰)은 **폐기**한다.
2. 첫 태스크의 마지막 확인은 다섯 번째 전체 코드 리뷰 대신 **자체 검토로 종결**한다 — 4회차 시점에 차단급 지적이 없었고 남은 지적이 주석 서술뿐이었다.
3. 대기 시간을 실제로 줄이는 일은 새 작업으로 잡는다: **재리뷰를 "이전 지적 + 수정분 + 영향 범위" 로 한정**하는 작은 변경.

## 근거

- 든 비용: 설계 리뷰 10회(예산 두 번 연장), 계획 리뷰 6회(한 번 연장), 첫 태스크에 코드 리뷰 4회 + 보안 리뷰 4회. 9월 11일 착수 → 9월 19일에도 첫 태스크 미커밋. 회차별 지적 수가 단조 감소하지 않았고 고칠 때마다 인접한 곳에서 새 지적이 나왔다.
- 새 로그의 실측 4줄: 코드 리뷰 1회 대기 839.5 / 896.5 / 938.4 / 1340.5초(약 14~22분), 전부 수정 필요 판정, 검토 대상 지문이 전부 달랐다 → "같은 내용 재호출 거절" 로 절약됐을 호출은 0건.
- 독립 검토(별 세션 모델) 요지:
  - 대기의 실제 원인은 측정 부재가 아니라 **비싼 검토를 반복하게 만드는 구조** — 래퍼가 재리뷰마다 새 세션을 띄워 이전 검토를 이어받지 않음(래퍼에 세션 이어가기 호출 0건 확인), 30분짜리 태스크 하나하나를 독립 승인 단위로 삼아 리뷰 고정비를 태스크 수만큼 지불, 리뷰 강도 기준이 위험이 아니라 줄 수(정본·미러 중복 포함), Medium 지적도 수정이 3줄을 넘으면 전체 재리뷰.
  - 설계가 목표를 뒤집었다 — 원래 목표는 대기 감소인데 "측정한 다음에만 줄인다" 로 바뀌어 실제 감소가 보류 축으로 밀렸다.
  - 전환 게이트가 가장 부적절 — 대기 감소나 부분 재검토의 안전성이 아니라 로그 작동 여부를 검증하고, "최근 28일에 재호출 거절 관측" 조건 때문에 불필요한 재호출을 하지 않는 정상 운영에서 오히려 닫히며, 판정마다 저장소 전체 계획 검증을 돌려 대기를 늘리면서 그 시간은 주 지표에서 빠진다.
  - 로그 변경은 추가 기능 없이도 쓸 수 있는 관측 결과를 내므로 살릴 가치가 있다. 단 "모든 호출 측정" 이라고 주장하면 안 된다.
- 진행자(Claude) 자기 평가: 설계 리뷰가 구현 세부를 짚을 때마다 절차를 문서 본문에 넣어 문서가 33KB→68KB 로 불었고, 계획 리뷰의 "태스크를 더 쪼개라" 를 받아 14개로 나누면서 각각을 승인 단위로 만들었다 — 비용을 키운 직접 원인.

## 다음 작업 후보 (싼 것부터, 독립 검토 제안)

| 대안 | 기대 효과 | 위험·조건 |
|---|---|---|
| 첫 리뷰는 전체, 후속은 이전 지적 폐쇄·수정 diff·영향 범위 중심 | 반복 탐색·재검증 감소 | 새 인터페이스·보안 경계·범위 변경이면 전체 검토로 복귀, 새 중대 결함 보고는 항상 허용 |
| 제한된 후속 검토에 중간 강도 적용(기존 `[EFFORT:medium]` 경로) | 회당 추론 비용 감소 | 탐지력 저하 가능 — 시간과 놓친 결함을 함께 비교 |
| 회차 상한 외에 누적 시간 예산 + 사람의 종결 결정(잔여 위험 수용·범위 축소·중단) 정식화 | 최악의 대기를 직접 제한 | 시간 초과를 통과로 간주하지 않는다. 검토 대상·남은 쟁점·수용 이유·승인자를 기록 |
| 응집된 태스크 여러 개를 하나의 승인 단위로 | 스위트·코드·보안 리뷰 고정비 감소 | 너무 크게 묶으면 검토가 어려워짐 |
| 문서 리뷰의 차단 범위를 실제 의사결정으로 제한 | 구현 세부를 문서에 넣고 재심받는 루프 감소 | 기존 래퍼에 이미 있는 제한이 지켜졌는지부터 확인 |

세션 이어가기(`resume --last`)를 단순히 켜는 것은 권하지 않는다 — 동시 작업에서 다른 세션을 이어받을 수 있고 이전 결론에 편향될 수 있다. 도입한다면 리뷰 대상과 세션을 명시적으로 결속해야 한다.

## 폐기되는 것의 처리

- spec·plan 문서는 삭제하지 않고 상단에 중단 표시를 단다(이력 보존). 설계의 축2·전환 게이트 절은 다음 작업의 입력으로 쓰지 않는다.
- 이 사이클에서 확립된 교훈은 유지: 설계 리뷰가 구현 실패를 짚을 때마다 절차를 본문에 넣으면 검토 표면이 자가증식한다 — 불변식·수용 기준만 설계에, 메커니즘은 구현 검증에.
