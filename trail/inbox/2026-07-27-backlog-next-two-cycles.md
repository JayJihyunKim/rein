# 2026-07-27 — 다음 두 사이클 (사용자 확정, 순서 고정)

이번 세션에서 사용자가 확정한 후속 작업 2건. **순서 고정** — ①을 먼저 하고 그 위에서 ②를 한다. 이유는 ② 자체가 ①이 다루는 연쇄의 전형이라, 방어 장치 없이 ②를 하면 훨씬 큰 연쇄가 난다.

---

## ① 설계 → 계획 → 테스트 연쇄 드리프트 (범위: **구조 재설계**)

**문제**: 설계를 고치면 계획이 안 맞고, 계획을 고치면 테스트가 안 맞는 연쇄. 사용자 보고로 **다른 프로젝트에서도 재발**.

**이번 세션 실측 근거** — 워치독 수리 1건에서:

| 원인 | 관측 |
|---|---|
| 계약 값의 대량 복제 | "2창/60초" 하나가 **12곳**에 리터럴로 존재 (설계서 정책·범위표·의사코드·미결질문·테스트전략, 계획서 매트릭스·작업지시·진단문, 코드, 테스트 이름·단언, 운영문서) |
| 검사기가 의미를 못 봄 | 커버리지 검사기는 **항목 이름 집합 일치**만 검증. 계획서 본문이 옛 동작을 그대로 서술해도 통과 — 매 단계 통과했는데 문서는 서로 모순이었고, 잡은 건 사람(codex) |
| 계획서의 역할 혼재 | 계획서가 **일회성 실행 지시**와 **지속되는 계약 대장** 두 역할을 겸함. 완료 후 앞은 이력이 되고 뒤는 최신이어야 하는데 한 문서라 매 수정 때 "이력인가 지시인가" 가 문제 |

**후보 방향** (설계 사이클에서 검토):
1. **폐기 계약 자동 탐지** — 항목 교체 시 옛 이름 + 옛 계약의 특징 문구를 저장소 전수 검색해 이력 구간 밖 잔존을 차단. 가장 값싸고 효과 큼 (사람이 15분 걸려 잡던 것의 상당수를 초 단위로).
2. **계약 대장 / 실행 지시 분리** — 대장을 계획서 본문에서 떼어내 "옛 지시와 새 계약의 공존" 상황 자체를 제거.
3. **값 단일화** — 설계서 한 표에만 값을 두고 나머지는 이름으로 참조. 테스트는 기본값을 하드코딩하지 말고 코드에서 읽기.

**한계 인정**: 산문 간 의미 모순은 기계가 전부 못 잡는다. 목표는 전부 자동화가 아니라 **기계적인 부분을 걷어내 사람이 볼 것을 의미 판단만 남기는 것**.

**주의**: rein 은 이미 관문이 많다. "검사를 하나 더 늘리는 게 정말 이득인가"부터 따져야 하며, 잘못하면 마찰만 늘고 체감 가치가 없다. 구상 단계에서 이 질문을 먼저 통과시킬 것.

## ② rein 산출물 경로 재배치 (주요 버전급)

**사용자 문제 제기**: rein 이 만드는 문서를 `.rein/` 안으로 모으는 게 낫지 않나.

**실측 (2026-07-27)**: 설치 시 사용자 저장소에 만드는 것은 **`.rein/`(+policy) 와 `trail/` 뿐**이다. `docs/` 는 만들지 않으며, `docs/specs|plans|brainstorms` 는 스킬·에이전트가 필요 시 생성한다 (brainstorming / spec-writer / codex-review / persona 스킬이 참조).

**진단 — 전부 `.rein/` 로 옮기는 건 아니다. 두 종류를 갈라야 한다.**

- **`docs/specs|plans|brainstorms` — 여기가 진짜 문제.** 사용자 프로젝트엔 이미 자기 `docs/` 가 있을 가능성이 높아 **이름 충돌**이 난다. 다만 이 문서들은 rein 의 상태가 아니라 **사용자 프로젝트의 설계 문서**다. 도구 내부 폴더에 묻으면 소유 관계가 뒤집힌다 → `docs/rein/` 처럼 **보이되 네임스페이스만 분리**하거나 경로를 설정 가능하게.
- **`trail/`** — 옮길 수는 있으나 손해가 있다. rein 이 파는 가치가 "증거를 남긴다" 인데 숨김 폴더는 발견성이 떨어진다. 최상위 유지가 낫고, 거슬리면 옮기기보다 **설정으로 빼는** 편.

**비용**: 경로가 훅·스크립트·스킬·테스트·문서에 하드코딩. 기존 설치 사용자 저장소도 **이사** 필요(업데이트가 옮겨주거나 양쪽 읽기). 배포·미러·패키징 규칙에도 경로가 박혀 있음. **주요 버전급.**
