# Orchestrator First — 메인 세션 지휘 기본 규칙

## 행동 강령

비trivial 개발 작업(구현·버그수정·리팩토링)에서는 메인 세션이 별도 지휘 서브에이전트를 거치지 않고 직접 지휘한다: 분해 가능성 판단 → 독립 WorkUnit 식별 → 워커 병렬 위임 → 결과 취합·통합 검증. 실질 구현은 워커가 한다. 분해·병렬 여부는 `agents/orchestrator.md` 의 4조건(`parallel-not-goal`)과 단일 워커 조항(`single-worker`)으로 판단하며 수치 임계는 없다. 단일 워커는 Worker 서브에이전트 하나에게 위임하는 것이지 지휘자의 자체 구현이 아니다. 워커 dispatch 금지목록·깊이 규칙·barrier 통합 절차·워커 매핑은 `agents/orchestrator.md` 를 그대로 따른다 — 워커별 리뷰 금지, 리뷰는 웨이브 하나가 끝날 때마다 부모가 취합해 1회. 워커 모델·병렬 강등은 단계가 바뀔 때마다 평문 1줄로 통지한다. 완료 기록(`trail/inbox/`)에 오케스트레이션 한 줄을 남긴다(비차단).

조사·문서·설계는 이 규칙의 트리거 밖이다 — 각 전담 에이전트의 몫.

---

## 1. 트리거와 적용 범위

이 규칙의 적용 대상은 개발 작업(구현·버그수정·리팩토링)이다. 조사·문서·설계는 각 전담 에이전트(researcher/docs-writer/spec-writer/plan-writer)의 몫이며 이 규칙의 트리거 밖이다. `answer-only-mode.md` §1 판정은 이 규칙과 독립적으로 그대로 유지되며, 이 규칙은 별도의 answer-only 판정 로직을 두지 않는다.

- **개발 작업** = `routing-map.md` 가 Builder 계열(`rein:feature-builder` / `rein:feature-builder-fix` / `rein:feature-builder-refactor`)로 매핑하는 작업 유형이다.
- **판정은 자기 분류(advisory)다.** "이 turn 이 비trivial 개발 작업인가"는 메인 세션이 스스로 판정하며 hook 강제가 없다. 실제로 편집을 막는 것은 이 판정과 별개로 동작하는 `pre-edit-discipline-gate.sh` 이고, 그 동작은 이 규칙으로 바뀌지 않는다.
- **answer-only 판정은 독립된 별개 층이다.** "이 turn 이 개발 작업인가"는 이 규칙의 트리거이고, "이 turn 이 answer-only 인가"는 `answer-only-mode.md` §1 이 판정한다. 이 규칙은 그 판정을 대체·우회하지 않는다. 개발 작업 트리거가 성립한 turn 이라도 아직 편집을 시작하지 않은 탐색 단계에서는 answer-only 층이 따로 유지될 수 있다.

---

## 2. 메인 세션이 직접 하는 네 가지

비trivial 개발 작업에서 메인 세션은 별도 서브에이전트를 거치지 않고 직접 다음을 수행한다. 지휘 모델은 사용자가 고른 세션 모델 그대로이며, 플러그인은 기본 agent 를 지정하지 않는다.

- (a) **분해 가능성 판단** — 작업을 나눌 수 있는지, 나누는 것이 이득인지 본다(§3).
- (b) **독립 WorkUnit 식별** — 서로 의존하지 않고 쓰기 범위(scope)가 겹치지 않는 단위를 가려낸다.
- (c) **워커 병렬 위임** — 독립 단위를 Worker 서브에이전트에게 동시에 맡긴다. 동시에 실행하는 묶음 하나를 웨이브라 부른다.
- (d) **결과 취합·통합 검증** — 워커 결과를 모아 확인하고, 통합된 결과가 원래 작업을 만족하는지 검증한다.

지휘자는 실질 구현을 스스로 하지 않는다 — 구현은 Worker 서브에이전트가 한다(유일한 예외는 §5 의 "워커 dispatch 자체 불가").

---

## 3. 분해·병렬 판단

판단 기준은 새로 만들지 않고 `agents/orchestrator.md` 의 정성 신호를 그대로 쓴다. 파일 수·단위 수 같은 수치 임계는 없다 — 판단은 매번 지휘자의 몫이다.

- **병렬 후보** — `parallel-not-goal` anchor 의 4조건을 모두 만족할 때: 독립 업무 + scope 실질 분리 + 선행 의존 없음 + 통합 비용 < 병렬 이득. 병렬화 자체는 목표가 아니다.
- **단일 워커** — `single-worker` anchor: 분해·병렬 실행이 이득보다 오버헤드가 크면 WorkUnit 을 1개로 유지한다.

"단일 워커"는 WorkUnit 을 1개로 줄여 그 1개를 Worker 서브에이전트 **하나에게 위임**하는 것이다. 지휘자가 워커 없이 스스로 구현하는 상태가 아니다.

---

## 4. 실행 규율과 워커 선택 — `agents/orchestrator.md` 참조

아래 네 가지는 `${CLAUDE_PLUGIN_ROOT}/agents/orchestrator.md` 가 정본이다. 이 규칙은 내용을 옮겨 적지 않고 가리키기만 한다 — 두 파일이 어긋나면 `agents/orchestrator.md` 가 이긴다.

- **워커 dispatch 금지목록 5종** (`prohibition-list` anchor) — 커밋·스테이징·리뷰/보안 증거 발급·trail 기록·stash. 전부 부모 소유다.
- **깊이 규칙** (`depth-rule` anchor) — 워커는 받은 작업을 또 다른 서브에이전트에게 위임하지 않는다.
- **barrier 통합 절차** (`barrier-procedure` anchor) — 검증 → 테스트 → 리뷰 → 커밋, 부모 소유.
- **워커 매핑** (`worker-mapping` anchor) — Builder / Reviewer / Security 닫힌 집합. 새 워커 에이전트를 만들지 않는다.

**읽는 법**: 참조 대상 본문에서 부모(Orchestrator) 자리는 기본 경로에서 메인 세션이 맡는다. 기본 경로는 메인 세션 → Worker 두 단계이며, 워커가 또 다른 서브에이전트를 낳지 않는다는 원칙은 같다.

**리뷰 시점**: 워커별 리뷰는 하지 않는다. 리뷰는 웨이브 하나가 끝날 때마다 부모가 취합해 1회(종속 웨이브가 둘 이상이면 웨이브 수만큼) 한다. 맨 끝으로 몰지 않는다 — 각 웨이브는 클린 트리에서 시작해야 한다. 워커로 실행된 에이전트의 리뷰 책임은 면제되는 것이 아니라 부모로 이관된다.

---

## 5. 워커 모델 판단과 강등 순서

워커 모델은 지휘자가 위임할 때마다 판단한다. 판단 축은 하나다: 복잡한 구조 판단이 필요한 변경·안전 민감 변경(보안·데이터 무결성 관련)은 지휘 모델과 동급 이상을, 정형화된 반복 편집·범위가 명확한 구현은 더 가벼운 모델도 무방하다고 지휘자가 판단한다. 이것은 규칙이지 자동 분류기가 아니다 — 기준 수치도, 이 판단을 읽는 코드도 없다.

원하는 모델을 쓸 수 없거나 병렬 dispatch 가 되지 않으면 아래 순서로 강등한다. 세 단계 모두 결과는 Worker 서브에이전트 하나에게 위임하는 것이며, 지휘자가 구현을 떠맡는 단계는 없다.

1. 원하는 워커 모델을 이 계정·환경에서 쓸 수 없음 → 가장 가까운 대체 모델로 바꿔 워커 1개에게 위임한다.
2. 대체 모델도 불가 → 지휘 모델(세션 모델)을 그대로 상속해 워커 1개를 띄운다.
3. 병렬·다중 워커 dispatch 자체가 불가하거나 실패 → 단일 워커 조항(§3)에 따라 Worker 서브에이전트 하나에게 직접 위임한다. 병렬만 포기한다.

**통지**: 단계가 바뀔 때마다 사용자에게 평문 1줄로 알린다 — "[작업 일부를] [원래 계획한 모델] 대신 [대체 방식]으로 진행합니다" 형태. silent 강등은 금지다(`agents/orchestrator.md` 의 감지·강등 절과 같은 원칙).

**3단계 밖 예외 — 강등이 아니다**: 이 세션에 Agent 도구 자체가 없는 등 Worker 서브에이전트를 하나도 띄울 수 없으면, 그 경우에 한해 메인 세션이 직접 수행한다. 이는 "강등"이 아니라 "워커 dispatch 자체 불가"라는 별개 사유이며, 사용자에게 그렇게 구분해 통지한다. 직접 수행하더라도 검증 → 테스트 → 리뷰 → 커밋 절차와 커밋 시점의 리뷰 요구는 그대로다.

## 6. 준수 관측 — 완료 기록 한 줄

작업을 마치면 `trail/inbox/YYYY-MM-DD-<slug>.md` 완료 기록 본문에 아래 한 줄을 넣는다:

```
- 오케스트레이션: N개 하위 작업(병렬 Y|N) — 강등 시 사유: <1줄> | 단일 처리 시: "분해 불필요(사유)"
```

- **비차단**: 이 한 줄은 어떤 훅도 검사하지 않는다. 누락돼도 `pre-edit-discipline-gate.sh`·`stop-session-gate.sh` 등 기존 게이트가 이를 이유로 차단하지 않는다.
- **기록 주체는 부모**(메인 세션)다 — 워커는 trail 에 쓰지 않는다(§4 금지목록).
- 위치가 `trail/inbox/` 인 이유: 매 작업마다 이미 생성되는 파일이고, `trail/index.md` 는 줄 수 상한이 있어 작업마다 늘어나는 기록을 담지 않는다.

## 7. 주입 조건과 옵션 경로

- **저장소별 opt-in**: 이 규칙은 `.rein/policy/rules.yaml` 에 `orchestrator-first: {enabled: true}` 가 있는 저장소에서만 세션 시작에 요약이 주입된다. 항목이 없거나 파싱에 실패하면 비활성이다.
- **DoD 기록**: DoD `## 라우팅 추천` 의 선택 필드 `orchestration:` 은 `routing-procedure.md` §6 이 정의한다. 그 필드는 결과를 기록할 뿐이며, 실행 계약의 정본은 이 파일이다.
- **옵션 경로**: `rein:orchestrator` 서브에이전트는 폐기되지 않았다. 오케스트레이션 전체를 별도 컨텍스트로 격리하고 싶을 때 메인 세션이 명시적으로 호출하는 경로로 남는다. 기본 경로는 이 규칙이다.
